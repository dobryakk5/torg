# ТЗ: Поисковые профили с плюс/минус-фразами

Доработка тендерного монитора `torg`. Заменяет плоский список `SEARCH_KEYWORDS`
на систему **поисковых профилей**: несколько независимых наборов плюс- и
минус-фраз, редактируемых в UI, с локальной балльной пост-фильтрацией и
ИИ-помощником для генерации фраз.

Основано на разборе от 2026-07-15: один гигантский запрос с сотнями исключений
не работает (цикл «широкое слово → мусор → исключение → исключение режет
полезное»). Вместо этого — 4–5 узких профилей + локальный скоринг карточки.

---

## 1. Цели

1. Искать в первую очередь **заказную ИТ-разработку онлайн** (сайты, веб,
   ПО/ИС, интеграции), во вторую — **сопровождение/поддержку** (отдельный
   профиль, включается по желанию).
2. Каждый тендер должен иметь понятную причину попадания в выборку:
   **по какому профилю и какой фразе он найден**.
3. Плюс/минус-фразы редактируются пользователем без правки кода.
4. Минус-фразы работают в двух режимах: жёсткое исключение и мягкий штраф
   (чтобы «поставка, внедрение и доработка ИС» не вылетала из-за слова «поставка»).
5. Профиль можно скопировать, включить/выключить; один профиль — дефолтный.
6. ИИ (через существующий `llm_provider`) помогает: генерирует черновик фраз
   по описанию услуг и проверяет фразы на риск ложных срабатываний.
   Черновики никогда не применяются автоматически — только после ручного
   подтверждения.

## 2. Не-цели (v1)

- Не переписываем `filter_engine.py` (8 фильтров) — только одна точка
  интеграции (см. §7.3).
- **Tenderplan в систему профилей не входит.** Tenderplan — управляемый
  подрядчиком источник со своим фильтром ключевых слов на их стороне;
  наши плюс/минус-фразы к нему не применяются, локальный пост-фильтр по
  профилям на его карточки не запускается, генератор «ключа» не делаем.
  Канал `sources/tenderplan.py` остаётся как есть, вне профилей.
- Не трогаем словарь `scoring_rules` (страница `/rules`) — это слой оценки
  Stage 1/2, профили — слой **поиска и первичного отбора**. Слои разные.

## 3. Терминология и семантика фраз

**Профиль** — именованный набор фраз + настройки. Поля: название, описание,
включён/выключен, дефолтный (ровно один), приоритет (порядок прогона).

**Фраза** — строка из одного или нескольких слов-масок:

- `*` в конце слова — усечение (стемминг): `разработк*` матчит
  «разработка/разработку/разработке…».
- `|` внутри слова — варианты: `битрикс|bitrix`.
- Многословная фраза матчит, если **все** слова найдены в тексте в пределах
  окна близости (по умолчанию слова стоят рядом, допускается разрыв
  `~N` слов; синтаксис `(разработк* сайт*)~2` — как в Tenderplan).
  Без явного `~N` окно = 1 (допускается одно слово между).

**Тип фразы:**

| Тип | Поведение |
|---|---|
| `plus` | Даёт баллы профильного скора; используется как поисковый запрос к источникам |
| `minus_hard` | Совпала → тендер отбрасывается этим профилем (в БД не сохраняем причину «профиль X», но пишем в лог) |
| `minus_soft` | Совпала → штраф к профильному скору, тендер остаётся |

**Вес фразы** — целое число. Дефолты: plus `+3`, minus_soft `−3`,
minus_hard веса не имеет. Пользователь может менять вес каждой фразы.

**Профильный скор тендера** = сумма весов всех сработавших plus и minus_soft
фраз профиля по тексту `title + primary_text`. Тендер «принят профилем», если
скор ≥ порога профиля (поле `min_score`, дефолт `3`) и не сработала ни одна
`minus_hard`.

Один тендер может быть принят несколькими профилями — храним все
(поле `matched_profiles`), лучший скор — основной.

## 4. Модель данных

`database.SCHEMA_VERSION`: **v6 → v7**. DDL в `init_db()` + `init_db.py`,
drop-списки в `reset_db()`.

```sql
CREATE TABLE IF NOT EXISTS search_profiles (
    id          SERIAL PRIMARY KEY,
    name        TEXT NOT NULL UNIQUE,
    description TEXT DEFAULT '',
    enabled     BOOLEAN NOT NULL DEFAULT TRUE,
    is_default  BOOLEAN NOT NULL DEFAULT FALSE,   -- ровно один TRUE (частичный уникальный индекс)
    priority    INT NOT NULL DEFAULT 100,          -- порядок прогона/отображения
    min_score   INT NOT NULL DEFAULT 3,            -- порог принятия тендера
    okpd2_codes TEXT[] NOT NULL DEFAULT '{}',      -- доп. канал ОКПД2 для ЭТОГО профиля; пусто = без ОКПД2
    price_target_lo INT,  -- ценовой коридор Ф2 (filter_engine); NULL = взять из config.PRICE_TARGET_LO/HI/PRICE_HARD_MAX
    price_target_hi INT,
    price_hard_max  INT,
    created_at  TIMESTAMPTZ DEFAULT now(),
    updated_at  TIMESTAMPTZ DEFAULT now()
);
CREATE UNIQUE INDEX IF NOT EXISTS ux_search_profiles_default
    ON search_profiles (is_default) WHERE is_default;

CREATE TABLE IF NOT EXISTS search_phrases (
    id          SERIAL PRIMARY KEY,
    profile_id  INT NOT NULL REFERENCES search_profiles(id) ON DELETE CASCADE,
    kind        TEXT NOT NULL CHECK (kind IN ('plus','minus_hard','minus_soft')),
    phrase      TEXT NOT NULL,                     -- с масками: "разработк* сайт*"
    weight      INT NOT NULL DEFAULT 3,            -- знак нормализуется по kind
    query_only  BOOLEAN NOT NULL DEFAULT FALSE,    -- TRUE: фраза только для запроса к источнику, не для локального скоринга
    local_only  BOOLEAN NOT NULL DEFAULT FALSE,    -- TRUE: только локальный скоринг, в источники не отправляется
    query_text  TEXT,                              -- ручное словоформа для ЕИС/витрин (иначе авто из маски)
    enabled     BOOLEAN NOT NULL DEFAULT TRUE,
    note        TEXT DEFAULT '',                   -- зачем добавлена / чем опасна
    created_at  TIMESTAMPTZ DEFAULT now(),
    UNIQUE (profile_id, kind, phrase)
);
```

В `tenders` добавить колонки (мягкая миграция `ALTER TABLE ... ADD COLUMN IF NOT EXISTS`):

```sql
profile_id      INT,          -- профиль с лучшим скором (NULL для ОКПД2-канала и старых записей)
profile_score   INT,          -- скор этого профиля
matched_profiles JSONB        -- [{"id":1,"name":"Сайты","score":7,"phrases":["разработк* сайт*"]}, ...]
```

Runtime-ключи `SEARCH_KEYWORDS`, `SPB_/EAT_/MOS_/MOSREG_SEARCH_KEYWORDS`
объявляются **legacy**: остаются как фоллбэк, если в `search_profiles` нет ни
одного включённого профиля (та же логика, что у `scoring_rules` →
`DEFAULT_BUCKETS`). Из списка разрешённых ключей `api_save_settings` не
удаляем до фазы 3.

## 6. Матчер (`search_profiles.py`, новый модуль)

Чистые функции + кеш профилей из БД (60 с, инвалидация при сохранении —
по образцу `filter_engine._load_rules()` / `invalidate_rules_cache()`).

```python
def match_profile(profile: Profile, text: str) -> MatchResult
    # MatchResult: accepted: bool, score: int, hits: [(phrase, weight)], hard_hit: str|None

def score_tender(tender: dict) -> list[MatchResult]   # по всем включённым профилям

def eis_queries(profile) -> list[str]     # plus-фразы → запросы ЕИС: маски убрать
                                          # ("разработк* сайт*" → "разработка сайта" — хранить
                                          # готовую словоформу в phrase; см. правило ниже)
def storefront_queries(profile) -> list[str]  # короткие точные фразы для витрин
```

Правила нормализации текста: lower, ё→е, схлопывание пробелов, токенизация по
не-буквенно-цифровым с сохранением дефисных слов («1С-Битрикс», «веб-сайт» —
один токен, плюс отдельные подтокены).

**Правило хранения фраз для внешних запросов.** ЕИС понимает морфологию, но не
маски, поэтому у фразы два представления:
- как хранится: `разработк* сайт*`;
- как отправляется в ЕИС/витрины: базовая словоформа = маска без `*`
  восстановлена по простому словарю окончаний (`разработк*` → `разработка`,
  `сайт*` → `сайт`). Если автоснятие маски даёт мусор, у фразы можно задать
  `query_text` вручную (доп. колонка TEXT NULL в `search_phrases`).
Фразы с `~N`, `|` и `local_only` в ЕИС не отправляются — только в локальный
скоринг.

Юнит-тесты матчера обязательны (`tests/test_search_profiles.py`):
кейсы из разбора — «разработка образовательной программы» не матчится П2;
«модульное здание» не матчится; «поставка, внедрение и доработка
информационной системы» принимается П2 с штрафом, но выше порога;
«сенсорная интеграция» отбрасывается П3.

## 7. Интеграция в конвейер

### 7.1 Stage 1 (`main.run_stage1`) — поиск только по профилям

Плоского глобального списка ключей больше нет как активного источника —
поиск управляется исключительно включёнными профилями. Для каждого
включённого профиля (в порядке `priority`):

- **Канал ЕИС по ключевым словам**: `eis_queries(profile)` вместо
  `kw_list`. В `_process_stage1_tenders` прокидывается `profile_id`;
  `matched_keywords` — как сейчас, плюс фраза.
- **Канал ОКПД2 — per-profile, опциональный**: если у профиля непусто поле
  `okpd2_codes`, для него дополнительно запускается
  `search_eis_by_okpd2(okpd2_codes=profile.okpd2_codes, ...)`; если пусто —
  канал ОКПД2 для этого профиля не запускается вообще. Глобального
  ОКПД2-канала (текущий `config.OKPD2_CODES` / `OKPD2_SEARCH_ENABLED`)
  больше нет — настройка становится частью профиля (сид: у П2 «Разработка
  ПО и ИС» заполнить `okpd2_codes` кодами 62.01/62.02/62.02.1/62.09/63.11
  из текущего `config.OKPD2_CODES`, у остальных — пусто).
- **B2B-Center**: те же `eis_queries(profile)` как поисковые фразы, канал
  включается флагом `SOURCE_B2B_ENABLED` (глобальным — витрина одна на всех
  профилей, как сейчас), но сам список фраз берётся из профилей.

**Локальный пост-фильтр** (ЕИС, ОКПД2, B2B, витрины): каждая пришедшая
карточка прогоняется через `score_tender()` по всем включённым профилям.
- Принята хотя бы одним профилем → сохраняем, пишем `profile_id` (профиль
  с лучшим скором), `profile_score`, `matched_profiles`.
- Не принята никем → **не сохраняем** (это и есть отсев мусора); отсев
  логируется счётчиком в `runs`. Это относится и к ОКПД2-каналу: он ловит
  по коду ОКПД2, а не по фразам, но карточка всё равно обязана пройти
  порог хотя бы одного профиля, иначе смысла в фильтрации нет.

Tenderplan (§2) в этот пост-фильтр **не попадает** — его карточки
сохраняются как есть, без `profile_id`.

Ручной запуск с `/control` (`SearchRunner`): выбор одного или нескольких
профилей вместо произвольных фраз; прогресс отображается по фразам
выбранных профилей, как сейчас.

### 7.2 Витрины (СПб, ЕАТ, mos, mosreg)

Полнотекстовый поиск по точной фразе → длинные фразы не работают. У профиля
нет отдельных списков: витринные запросы = plus-фразы профиля из ≤2 слов
(после снятия масок). Витрины включаются/выключаются как сейчас (глобальные
флаги), список фраз для них строится из включённых профилей.

### 7.3a Ценовой коридор Ф2 — настраивается в профиле

Каждый профиль может переопределить целевую зону НМЦК и жёсткий максимум Ф2
(`price_target_lo/hi`, `price_hard_max` в `search_profiles`; поля пусты по
умолчанию — тогда действует общий `config.PRICE_TARGET_LO/HI/PRICE_HARD_MAX`
из `/control`). При принятии тендера профилем (`search_profiles.filter_and_tag`)
границы лучшего профиля копируются на тендер (`profile_price_lo/hi/hard_max`,
персистентные колонки `tenders`) и используются `filter_engine._filter_finance`
вместо глобальных — так Stage 1 и Stage 2 видят одни и те же границы.
Редактируется на `/profiles` в блоке настроек профиля.

### 7.3 Связь с filter_engine

По образцу LLM-триажа (мягкая корректировка): если `profile_score` ≥
`min_score + 4` → Ф1 +1; если тендер прошёл только с minus_soft-штрафами
(были минус-хиты) → Ф1 −1. Реализация — в месте, где `filter_engine` читает
`tender["llm_triage"]`; добавить чтение `tender["profile_score"]`.
Балльную модель из разбора (+4 разработка ПО/ИС, +3 сайт, −5 лицензия…)
реализуют **веса фраз**, отдельного второго скоринга не строим.

### 7.4 Дашборд `/`

- Фасет «Профиль» рядом с фасетом по поисковой фразе.
- В карточке тендера: бейдж профиля + топ-3 сработавших фраз (из
  `matched_profiles`), чтобы была видна причина попадания.

## 8. UI: страница `/profiles`

Новая страница (пункт меню между «Управление» и «Правила»). На `/control`
блок «Поисковые фразы (ЕИС)» заменяется ссылкой на `/profiles` + селектором
профиля для ручного запуска.

### Список профилей
Таблица: имя, вкл/выкл (тумблер), «по умолчанию» (радио), приоритет,
счётчики фраз (+/−), найдено тендеров за 30 дней, кнопки:
**Копировать** (создаёт «Имя (копия)» со всеми фразами, выключенную),
**Удалить** (с подтверждением; дефолтный и последний включённый удалить нельзя),
**Создать профиль**.

### Карточка профиля
- Поля: имя, описание, порог `min_score`, приоритет, коды ОКПД2 (опционально,
  многострочное поле "по одному коду на строку"; пусто = без ОКПД2-канала).
- Две таблицы фраз (плюс / минус): фраза, вес, режим (для минуса hard/soft),
  флаги `query_only`/`local_only`, вкл/выкл, заметка, удалить. Добавление —
  строка ввода + массовая вставка «по одной на строку» (как текущий textarea).
- **Линтер фраз** (при добавлении/сохранении, предупреждение, не блокировка):
  - слишком общая plus-фраза: односложная без квалификатора из стоп-списка
    (`программ*, модул*, платформ*, функционал*, ИТ, IT, систем*, баз* данн*
    в форме создан*/внедрен*`) → «даст много мусора, добавьте уточнение»;
  - опасная hard-минус фраза (`строител*, ремонт, поставк*, приобретени*,
    сопровожден*, доступ*` без уточнения) → «может удалить полезные закупки,
    рекомендуем minus_soft или узкое сочетание»;
  - дубли и почти-дубли (одинаковая нормализованная форма) внутри профиля;
  - непарные скобки / `~` без числа — ошибка, блокирует сохранение.
- **Предпросмотр**: кнопка «Прогнать по базе» — матчер по последним N (500)
  тендерам в БД, две колонки: «принято» (с фразами-причинами) и «отсеяно
  hard-минусами». Без походов во внешние источники — мгновенно и бесплатно.

### ИИ-помощник (в карточке профиля)
1. **«Сгенерировать фразы»**: textarea «Опишите услуги своими словами» →
   `llm_analyzer.suggest_profile_phrases(text, existing_phrases)` (модель
   `OPENROUTER_TRIAGE_MODEL`) → черновик plus/minus-фраз с весами и
   пояснениями. Каждая строка — чекбокс; применяются только отмеченные.
   В промпт зашить правила гигиены из §5 (запрещённые конструкции,
   опасные минусы) и синтаксис масок.
2. **«Проверить фразы»**: LLM получает список фраз профиля, возвращает для
   каждой рискованной — примеры ложных срабатываний (по образцу разбора:
   `разработк* программ*` → «программа газификации…»). Выводится рядом с
   линтером.

### API (`web_app.py`)
```
GET    /api/profiles                    список + счётчики
POST   /api/profiles                    создать
PATCH  /api/profiles/{id}               имя/описание/enabled/is_default/priority/min_score/okpd2_codes
POST   /api/profiles/{id}/copy          копия (выключенная)
DELETE /api/profiles/{id}
PUT    /api/profiles/{id}/phrases       полная замена списка фраз (транзакция)
POST   /api/profiles/{id}/preview       {limit} → прогон по БД
POST   /api/profiles/{id}/ai-suggest    {description} → черновик фраз
POST   /api/profiles/{id}/ai-review     → риски по текущим фразам
```
Смена `is_default` — атомарно (снять со старого, поставить новому).
Любое сохранение фраз → инвалидация кеша матчера.

## 9. Этапы и приёмка

**Фаза 1 — ядро** (БД + матчер): схема v7, сид-профили, `search_profiles.py`,
юнит-тесты матчера. Приёмка: `python -m pytest tests/test_search_profiles.py`;
`init_db.py` на существующей базе проходит без потери данных, старый
`SEARCH_KEYWORDS` импортирован в П6.

**Фаза 2 — конвейер**: интеграция в `run_stage1` + `SearchRunner` (поиск
только по профилям, ОКПД2 — per-profile канал, Tenderplan не участвует),
пост-фильтр всех участвующих каналов, колонки в `tenders`, корректировка Ф1.
Приёмка: `python main.py --stage1 --test` на сервере — в логе видно
профили/фразы/отсев; в БД у новых тендеров заполнены `profile_id`,
`matched_profiles`; тендеры от Tenderplan сохраняются без `profile_id`,
как раньше.

**Фаза 3 — UI**: `/profiles`, правки `/control` и дашборда, линтер,
предпросмотр, ИИ-помощник.
Приёмка: создать профиль → скопировать → отредактировать фразы → назначить
дефолтным → прогнать предпросмотр → запустить ручной поиск по профилю с
`/control`; линтер ругается на `разработк* программ*` и на hard-минус `ремонт`.

Перед коммитом каждой фазы: `python -m py_compile` изменённых файлов,
рендер шаблонов через `web_app.templates.env` (соглашения CLAUDE.md).

## 10. Риски и решения

| Риск | Решение |
|---|---|
| ЕИС не понимает маски/`~N` | Двойное представление фразы: маска для локального матчинга, словоформа для запроса (`query_text` при необходимости) |
| Профилей нет/все выключены | Фоллбэк на legacy `SEARCH_KEYWORDS` (как `scoring_rules` → дефолты) — только как аварийный случай, в штатном режиме поиск идёт исключительно по профилям |
| Hard-минус съедает полезное | Линтер + рекомендация minus_soft; предпросмотр показывает отсеянное |
| Рост числа запросов к ЕИС (больше фраз) | `REQUEST_DELAY` не трогаем; дедуп по `purchase_number` уже есть; фразы профилей П2/П3 узкие — реальный рост умеренный; счётчик запросов в лог |
| Один тендер найден дважды разными профилями | Дедуп `seen_this_run` + `matched_profiles` накапливает все профили |
| Профиль без `okpd2_codes` теряет то, что глобальный ОКПД2-канал раньше ловил | При сидировании перенести текущие `config.OKPD2_CODES` в `okpd2_codes` профиля П2, чтобы не потерять охват |
