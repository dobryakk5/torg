# ТЗ: бесплатный LLM-анализ + агрегация ЗМО без платного Tenderplan

Дата: 2026-07-14. Основано на аудите кода и БД (3231 тендер, 853 с текстом ТЗ,
LLM-триаж ни разу не запускался, notified_at = 0 у всех).

Цель: отказаться от Tenderplan, самостоятельно агрегировать закупки
(в первую очередь малого объёма — ЗМО) и анализировать их бесплатными
моделями OpenRouter. Реагировать на ЗМО быстро (котировочные сессии живут ~24 ч).

---

## Блок 0. Починка конфигурации (5 минут, без кода)

Сейчас триаж мёртв из-за трёх вещей в `.env`:

1. Ключ лежит как `openrouter=...`, а `config.py:87` читает `OPENROUTER_API_KEY`.
   → Переименовать строку в `OPENROUTER_API_KEY=...`.
2. `LLM_TRIAGE_ENABLED=0` → поставить `1`.
3. `OPENROUTER_TRIAGE_MODEL=tencent/hy3:free` — проверить, что слаг существует:
   `curl -s https://openrouter.ai/api/v1/models | jq -r '.data[].id' | grep ':free'`.
   Если нет — заменить на реальный (кандидаты: `deepseek/deepseek-chat-v3-0324:free`,
   `meta-llama/llama-3.3-70b-instruct:free`, `qwen/qwen3-235b-a22b:free`).

Смоук-тест: `python main.py --triage --limit 5 --test` — в логе должны появиться
строки «Триаж [БЕРУ/…]».

Ограничения бесплатных моделей OpenRouter (учитывать во всех блоках):
- ~50 запросов/день при балансе < $10; 1000/день при балансе ≥ $10 (разово положить $10 — их не тратят);
- жёсткие 429 при бурстах; модели периодически уходят в оффлайн;
- `response_format: json_object` поддерживают не все — нужен фолбэк.

## Блок 1. Надёжность LLM-канала (`llm_provider.py`)

Сейчас `complete()` делает один HTTP-запрос без ретраев: любой 429 = молча
потерянная карточка.

Доработки в `_complete_openrouter()` / `complete()`:

1. **Ретраи**: на 429 и 5xx — до 3 повторов с экспоненциальным backoff
   (5с → 20с → 60с), уважать заголовок `Retry-After`, если пришёл.
2. **Цепочка фолбэк-моделей**: новая настройка
   `OPENROUTER_FALLBACK_MODELS` (список слагов через запятую, env + runtime).
   Если основная модель отдала 429/404/пустой ответ после ретраев — пробуем
   следующую из списка. Логировать, какая модель реально ответила
   (её же писать в `llm_triage_model`).
3. **Фолбэк json_mode**: если модель вернула 400 на `response_format` —
   повторить запрос без него (`parse_json()` уже терпит мусор вокруг JSON).
4. **Дневной счётчик запросов**: инкрементировать счётчик в таблице `settings`
   (ключ `LLM_REQUESTS_<YYYY-MM-DD>`); при достижении
   `LLM_DAILY_REQUEST_LIMIT` (default 900) — прекращать LLM-шаги до завтра
   с внятным логом. Защита от выжигания лимита в цикле.

Новые ключи в `config.py` + в allowed-список `web_app.api_save_settings`:
`OPENROUTER_FALLBACK_MODELS`, `LLM_DAILY_REQUEST_LIMIT`.

Приёмка: обрыв сети/подмена ключа не роняет пайплайн; в логах видны ретраи
и переключение модели.

## Блок 2. Батч-триаж (`llm_analyzer.py`, `main.run_triage`)

Сейчас 1 карточка = 1 запрос. С лимитом 50–1000/день бэклог из ~1500 активных
карточек так не прогнать. Батчинг сокращает расход в 8–10 раз.

1. Новая функция `triage_tenders_batch(tenders: list[dict]) -> dict[str, dict]`:
   - упаковывает до `LLM_TRIAGE_BATCH_SIZE` (default 8) карточек в один промпт;
     каждая карточка нумеруется своим `purchase_number`;
   - текст карточки резать до `LLM_TRIAGE_TEXT_CHARS // 2` (батч не должен
     вылезать за контекст бесплатной модели);
   - формат ответа: JSON-массив `[{"id": "<purchase_number>", "verdict": ...,
     "fit": ..., "resale": ..., "category": ..., "reason": ...}, ...]`;
   - валидация: каждый `id` должен совпасть с отправленным; карточки без ответа
     или с битым JSON — вернуть в очередь и добить одиночным `triage_tender()`
     (существующий путь сохранить как фолбэк);
   - `max_tokens` ≈ 120 × размер батча.
2. `run_triage()` переключить на батчи; сохранение результата не меняется:
   `db.save_triage()` + пересчёт `run_stage1_filters` + `db.update_stage1_after_triage()`.
3. Прогон бэклога: `python main.py --triage --limit 2000`.
   `get_triage_candidates()` уже отдаёт только не-NO-GO без разметки —
   это ~1590 карточек ≈ 200 батч-запросов ≈ один день бесплатного лимита.

Приёмка: после прогона `select llm_triage_verdict, count(*) from tenders group by 1`
показывает разметку; GO-вкладка дашборда очищается от перекупа лицензий
(Kaspersky/TrueConf) и нецелевых лотов (котельные, тренажёры).

## Блок 4. Коннекторы ЗМО (новые файлы в `sources/`)

ЗМО (до 600 тыс. по 44-ФЗ) почти не публикуются на zakupki.gov.ru — они на
витринах. Целевые площадки (из ~190 в `tenderplan/filtry_zakupok_i_ploshchadki.md`
для ИТ-профиля реально нужны только эти):

| Приоритет | Площадка | Модуль | Префикс номера | platform |
|---|---|---|---|---|
| 1 | Портал поставщиков Москвы zakupki.mos.ru | `sources/mos_supplier.py` | `MOS-<id>` | `ПП Москвы` |
| 2 | ЕАТ Берёзка agregatoreat.ru | `sources/eat.py` | `EAT-<id>` | `ЕАТ` |
| 3 | Электронный магазин СПб estore.gz-spb.ru | `sources/spb_estore.py` | `SPB-<id>` | `ЭМ СПб` |
| 4 | Электронный магазин МО market.mosreg.ru | `sources/mosreg.py` | `MOSREG-<id>` | `ЭМ МО` |

Порядок работ для КАЖДОЙ площадки:

1. **Разведка** через `probe_sources.py` (он для этого и создан): все четыре —
   SPA с JSON-бэкендом; найти list-эндпоинт, параметры пагинации/фильтров
   (цена, категория/КПГЗ, статус «приём заявок»), формат карточки.
   Зафиксировать результат разведки комментарием в шапке модуля.
   Важно: рунет-домены из локальной песочницы недоступны — разведку и отладку
   вести на сервере.
2. **Коннектор**: функция `search_<name>(keyword, price_from, price_to, pages) ->
   list[dict]` в стандартном формате карточки (`scraper._parse_card`):
   `purchase_number, title, customer, price, law_type, deadline, published_at,
   url, platform, primary_text, region, matched_keywords`.
   - `law_type`: `"ЗМО"` (новое значение, проверить что фильтры/UI его переживают);
   - дедуп гарантируется префиксом номера;
   - бережный скрейпинг: `config.REQUEST_DELAY`, ретраи с backoff;
   - у котировочных сессий ПП Москвы дедлайн часто «сегодня+1» — поле deadline
     обязательно.
3. **Интеграция в `run_stage1()`**: канал по образцу B2B (`main.py:324-349`),
   флаги `SOURCE_MOS_ENABLED`, `SOURCE_EAT_ENABLED`, … (env + runtime settings,
   чекбоксы в `/control`, ключи в allowed-список `api_save_settings`).
4. **Stage 2**: документы качаем только для ЕИС (как сейчас); ЗМО-лоты скорим
   по тексту карточки/страницы. Если API площадки отдаёт вложения — отдельной
   итерацией позже.

Приёмка по каждой площадке: `python main.py --stage1 --test` находит и скорит
лоты площадки; карточки видны на дашборде с правильной platform.

## Блок 5. Быстрый цикл для ЗМО (`main.py`, демон)

Демон сейчас крутит всё раз в `SCHEDULE_HOURS=3` — для сессий на 24 ч это поздно.

1. Новая функция `run_fast_cycle()`:
   - опрашивает ТОЛЬКО быстрые источники (коннекторы Блока 4), `only_new=True`;
   - новые карточки сразу батч-триажит (Блок 2), без ожидания общего Stage 1.5;
   - критерий мгновенного уведомления: триаж `БЕРУ` + `filter_decision != 'NO-GO'`
     + цена в целевом коридоре → немедленно в Telegram
     (`send_tender_message` с primary-скором, пометка «⚡ ЗМО, дедлайн близко»),
     проставить `notified_at`;
   - весь цикл должен укладываться в 2–3 минуты (карточек за 20 минут немного).
2. Расписание в `main()` (демон-ветка, `main.py:1087+`):
   - `schedule.every(config.FAST_CYCLE_MINUTES).minutes.do(run_fast_cycle)`,
     `FAST_CYCLE_MINUTES` default 20 (env + runtime, редактируется в `/control`);
   - полный `run_once()` остаётся раз в 3 ч, аналитика в 04:00 — без изменений;
   - защита от наложения: если `run_once` уже работает — быстрый цикл
     пропускает итерацию (флаг-lock в модуле).
3. **Проверить Telegram-доставку** (у всех 3231 лотов `notified_at IS NULL` —
   похоже, боевых отправок ещё не было): разовый тест
   `send_startup_message` / отправка одного лота, убедиться что
   `TELEGRAM_BOT_TOKEN`/`TELEGRAM_CHAT_ID` рабочие.

Приёмка: новый ЗМО-лот с вердиктом БЕРУ прилетает в Telegram в течение
FAST_CYCLE_MINUTES + 2 мин после публикации на витрине.
