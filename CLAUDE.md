# CLAUDE.md

Гайд для AI-агентов и разработчиков по проекту **Тендерный монитор** (`torg`).

## Что это

Система мониторинга госзакупок и тендеров под профиль ИТ-подрядчика
(1С-Битрикс, сайты, интеграции с 1С, серверы, ИТ-оборудование с настройкой).
Собирает закупки из открытых источников, прогоняет через 8-фильтровый движок
оценки, лучшие отправляет в Telegram. Управление и аналитика — через веб-панель.

Язык кода и интерфейса — русский. Все комментарии, логи и UI на русском.

## Стек

- **Python 3** + `requests` + `BeautifulSoup` (скрейпинг), `schedule` (демон)
- **PostgreSQL** через `psycopg2` (пул соединений в `database.py`)
- **FastAPI** + `uvicorn` + `Jinja2` — веб-панель (`web_app.py`, `templates/`)
- **Anthropic Claude API** (`llm_analyzer.py`) — детальный разбор топ-кандидатов
- **Telegram Bot API** (`notifier.py`, `telegram_decisions.py`) — уведомления + кнопки решений

## Запуск

```bash
python init_db.py                 # ОДИН РАЗ: создать схему + засеять дефолты/правила
uvicorn web_app:app --host 0.0.0.0 --port 8000 --reload   # веб-панель
python main.py --once             # полный цикл stage1 + триаж + stage2
python main.py --test             # то же без отправки в Telegram
python main.py                    # демон по расписанию (SCHEDULE_HOURS)
python main.py --stage1|--triage|--stage2|--stage3|--analytics
python main.py --reset-db         # DROP+пересоздание схемы (осознанно!)
```

Секреты — в `.env` (`DATABASE_URL`/`PG_*`, `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID`).
LLM: по умолчанию **OpenRouter** — задай `OPENROUTER_API_KEY` (модели
`OPENROUTER_TRIAGE_MODEL`/`OPENROUTER_DEEP_MODEL`, по умолчанию `openai/gpt-4o-mini`
и `openai/gpt-4o`, меняются в `/control`). Для прямого Claude: `LLM_PROVIDER=anthropic`
+ `ANTHROPIC_API_KEY`. См. `config.py` и `llm_provider.py`.

## Конвейер (воронка)

1. **Stage 1** (`main.run_stage1`) — массовый сбор карточек из источников,
   быстрый скоринг по карточке (без скачивания ТЗ). Каналы:
   - ЕИС по ключевым словам (`scraper.search_eis`)
   - ЕИС по кодам ОКПД2 (`scraper.search_eis_by_okpd2`)
   - **B2B-Center** (`sources/b2b_center.py`) — коммерческие + 223-ФЗ вне ЕИС, под флагом
2. **Stage 1.5 — LLM-триаж** (`main.run_triage`) — дешёвый массовый проход по
   собранным карточкам через `llm_analyzer.triage_tender` (модель `OPENROUTER_TRIAGE_MODEL`):
   вердикт БЕРУ/ЧАСТИЧНО/МИМО + флаг перекупа + причина. Ловит ложные совпадения
   ключевых слов и перекуп лицензий/железа. Результат пишется в колонки `tenders.llm_triage_*`
   и **мягко** корректирует Ф1 (профиль) на ±1–2 балла. Флаг `LLM_TRIAGE_ENABLED`.
3. **Stage 2** (`main.run_stage2`) — для кандидатов с высоким первичным скором:
   скачивание страницы/ТЗ (ТЗ — только для ЕИС), извлечение условий, детальный
   скоринг, LLM-анализ топов (`OPENROUTER_DEEP_MODEL`), отправка в Telegram.
4. **Stage 3** (`main.run_stage3`) — после дедлайна тянет результаты/победителей.
5. **Аналитика** (`run_analytics`) — ценовые коридоры, карточки заказчиков,
   детектор изменений ТЗ.

Дедуп по `purchase_number` (у B2B он вида `B2B-<id>`, не пересекается с ЕИС).

## Движок фильтров (`filter_engine.py`) — ВАЖНО

8 измерений, каждое 1–5 баллов (итог 8–40), решение GO/CAUTION/NO-GO + стоп-факторы:

1. Профиль задачи · 2. Финансовый вход · 3. Объём и границы работ · 4. Сроки и SLA
· 5. Требования к участнику · 6. Признаки «под своего» · 7. Поставка/перекуп ·
8. Договорные риски.

Особенности скоринга (важно при правках):
- **Ценовой коридор** (Ф2, конфиг `PRICE_TARGET_LO/HI`, `PRICE_HARD_MAX`): целевая
  зона 100–500 тыс — бонус; вне неё, но ≤ `PRICE_HARD_MAX` (1 млн) — штраф 1 балл;
  выше — **стоп-фактор → NO-GO** (не хватит обеспечения). Не путать с `PRICE_MIN/MAX`
  (границы ПОИСКА в ЕИС).
- **Stage 1 без ТЗ**: Ф3/Ф5/Ф6 нельзя проверить по карточке — держатся нейтральными
  (3), не раздувая итог. Решение на Stage 1 считается по оцениваемым Ф1,Ф2,Ф4,Ф7,Ф8
  (см. `_decision` с учётом `stage`).
- **Страж перекупа** (`_is_resale_without_service`): «поставка/предоставление
  лицензий», поставка оборудования/товара без работ по настройке/доработке/внедрению
  → Ф1 ≤ 2, даже если в названии есть «Битрикс/1С/сервер».
- **LLM-триаж** мягко двигает Ф1: вердикт из `tender["llm_triage"]` (БЕРУ +2, ЧАСТИЧНО −1,
  МИМО/перекуп −2), итоговое решение по-прежнему по сумме фильтров.

**Фразы вынесены из кода в редактируемый словарь** (таблица `scoring_rules`):
- Источник истины по умолчанию — `DEFAULT_BUCKETS` в `filter_engine.py`
  (ключ `(номер_фильтра, корзина)` → список фраз).
- При наличии записей в `scoring_rules` движок берёт фразы из БД (кеш 60с,
  `_load_rules()`), иначе **откатывается на дефолты** — поэтому система работает
  даже до миграции/наполнения.
- Правило поддерживает **стражи контекста**: `unless` (не срабатывать рядом с
  фразой) и `require` (только если рядом есть фраза). Пример «Битрикс-сайт да,
  Битрикс-лицензии нет»: `strong: битрикс|bitrix` + `unless=лиценз`.
- `term` поддерживает `|` (любой из вариантов) и `*` (wildcard для корзин из
  `WILDCARD_BUCKETS`).
- Редактируется в UI на странице **`/rules`**; кеш сбрасывается
  `filter_engine.invalidate_rules_cache()` при сохранении.
- `knowledge_base.kb_risk_rules` — отдельный слой персональных взвешенных
  stop/warn/boost-правил (страница `/kb`), вливается в фильтр №1.

При изменении набора корзин синхронизируй: `DEFAULT_BUCKETS`, `BUCKET_LABELS`,
карту `dim_buckets` в `templates/rules.html`.

## База данных

- Версия схемы — `database.SCHEMA_VERSION` (сейчас `v6`). При добавлении таблиц
  **подними версию** и добавь DDL в `init_db()` + в drop-списки `reset_db()`
  (и в `init_db.py`). Миграция неинвазивна: `CREATE TABLE IF NOT EXISTS`, на
  старте `check_db()` требует текущую версию и просит запустить `init_db.py`.
- Основные таблицы: `tenders`, `filter_scores`, `scoring_rules`, `runs`,
  `decisions`, `customers`, `price_corridors`, `settings`, `kb_*`.
- Runtime-настройки в таблице `settings` переопределяют env (`config.get_runtime`),
  редактируются в `/control`; список разрешённых ключей — в `web_app.api_save_settings`.

## Веб-панель (`web_app.py` + `templates/`)

- `/` — дашборд тендеров (вкладки GO/CAUTION/NO-GO, фасет по поисковой фразе, фильтры по Ф1–Ф8)
- `/control` — настройки, запуск задач, выбор источников/ключевых слов, история
- `/rules` — редактор словаря фраз фильтрации (term/корзина/unless/require/вкл)
- `/kb` — база знаний (контракты, компетенции, оборудование, правила рисков, шаблоны)
- `/analytics`, `/customer/{inn}`, `/tender/{number}`

## Соглашения и подводные камни

- **Карточка тендера — единый `dict`** во всех источниках (см. `scraper._parse_card`):
  `purchase_number, title, customer, price, law_type, deadline, published_at, url,
  platform, primary_text`. Новый источник = функция, возвращающая такой `dict`,
  + канал в `run_stage1`. Поле `platform` различает источники (`"ЕИС"`, `"B2B-Center"`).
- Stage 2 скачивает ТЗ **только для ЕИС** (`platform == "ЕИС"`); прочие скорятся по тексту страницы.
- Скрейпинг бережный: `config.REQUEST_DELAY`, ретраи с backoff. Не запускать часто.
- Без сети к рунет-доменам код не протестировать локально из песочницы — проверять на сервере.
- Перед коммитом: `python -m py_compile <изменённые .py>`; для шаблонов — рендер через `web_app.templates.env`.

## Внешние источники: что и откуда

- **ЕИС (zakupki.gov.ru)** — все 44-ФЗ и 223-ФЗ публикуются здесь по закону;
  агрегаторы (Tenderplan и пр.) по госзакупкам ничего сверх ЕИС не дают.
- **Вне ЕИС** (имеет смысл добавлять): коммерческие закупки (B2B-Center — подключён,
  Фабрикант), малые закупки (Портал поставщиков zakupki.mos.ru — товар-центричен,
  для ИТ-услуг даёт мало). Банкротные торги — не профиль.
